# GAME_SITE_STARTER v2.6 Stage 1 Change Plan

This is a Human-review change plan only. Do not implement before explicit Human approval.

## Scope Verdict

Proposed v2.6 Starter scope: MINIMAL / APPROPRIATE.

Reason: the plan fixes repeated production-hardening gaps at the technical boundary while preserving v2.5 architecture. It does not redesign the Starter, move methodology into runtime code, or introduce a media workflow system.

## Package D Technical Fix: Site Chrome Asset Separation

### Observed Production Failure

A valid header logo rendered as semantic `<img alt="...">` was rejected as page content media. The file existed; the role classification was wrong.

### Technical Root Cause

`scripts/media-validation.ts` function `collectMediaHtmlErrors` scans every `<img>` in page HTML and requires its `src` to be an existing `/media/` file. This assumes all images are content media. `Header.astro` currently renders text mark only, so v2.5 tests never exercised a header logo image.

Affected v2.5 files:

- `scripts/media-validation.ts`
- `scripts/audit-build.ts`
- `src/core/html-audit.ts`
- `src/components/Header.astro`
- `src/config/schema.ts`
- `src/core/brand.ts`
- `src/layouts/BaseLayout.astro`
- `tests/media-audit.test.ts`
- `tests/html-audit.test.ts`
- `tests/navigation.test.ts`
- `tests/brand.test.ts`

### Proposed Minimal Change

After Human approval:

1. Split generated HTML media audit by role:
   - Content media validation applies to Starter-owned content media markup: `figure.game-media[data-media-id]` and fixed `data-media-placement` containers.
   - Site chrome validation applies to configured logo/favicon/header/footer brand assets.
2. Stop using the broad all-page `<img>` scan in `collectMediaHtmlErrors` as a content media gate.
3. Preserve global accessibility audit in `collectBuildHtmlAuditErrors`: every `<img>` still needs `alt`.
4. Add a small config contract for optional logo path only if implementation proves Header needs one:
   - keep current text mark path valid;
   - allow semantic logo image with meaningful `alt`;
   - allow decorative mark treatment where appropriate;
   - avoid a `ChromeAssetRegistry` or generic asset role engine.
5. Validate configured logo existence separately from content media:
   - logo path should resolve to a safe public asset;
   - favicon remains validated as required build artifact;
   - header home link must keep an accessible name.

### Stable Core Analysis

- Why all future projects inherit it: every branded game site needs site chrome that is not article/media content.
- Production evidence: header logo `<img>` misclassified as content media.
- Project-edge alternative: CSS `background-image` workaround exists but is not acceptable because semantic branding image must remain possible.
- API/schema impact: small optional config extension may be needed; no media manifest change required.
- Coupling impact: lower coupling by separating chrome asset checks from content media checks.
- Regression protection: media audit tests plus Header rendering/accessibility tests.

### Regression Plan

Required tests after approval:

- Header semantic logo renders as `<img>` and preserves accessible brand semantics.
- Header home link keeps an accessible name.
- Configured logo file exists and passes chrome asset validation.
- Content-media audit ignores the header logo as content media.
- Invalid article hero path still fails.
- Raw unsupported remote content image still fails when rendered as content media.
- Every `<img>` still requires `alt`.
- Text-mark default path still passes for projects without logo.

### Classification

MUST FIX.

## HIGH PRIORITY Media Readiness Signal

### Observed Production Failure

v2.5 can technically pass with little or no integrated media even when upstream planning classified media as HIGH PRIORITY.

### Technical Root Cause

Starter validates only runtime content media manifest/rendered output. It does not read planning media lifecycle state. That was safe for v2.5, but v2.6 SOP now requires unresolved high-priority media to stay visible through planning/reconciliation without moving lifecycle into Runtime Page Inventory.

Affected v2.5 files:

- `scripts/validate-site.ts`
- `src/core/site-validation.ts` or a new adjacent validation helper
- `src/data/media/catalog.ts`
- `src/data/schemas/media.ts`
- `tests/site-validation.test.ts`
- `tests/media.test.ts`
- New tests for optional media decision table validation

### Proposed Minimal Change

After Human approval:

1. Add optional technical validation for `MEDIA_DECISION_TABLE.md` or a structured sidecar derived from it, if present in a real project.
2. Key rows by existing Page Inventory `pageId` or route.
3. Validate only technical consistency:
   - referenced page exists;
   - `HIGH PRIORITY` homepage unresolved emits a blocking validation error unless the table records explicit waiver/no-media exception state;
   - `HIGH PRIORITY` guide/article unresolved emits warning or revise signal according to approved severity;
   - `RECOMMENDED` unresolved remains non-blocking informational output;
   - `NO MEDIA NEEDED` remains valid when explicitly represented with rationale.
4. Do not add media fields to Runtime Page Inventory.
5. Do not encode rights approval logic in Starter.
6. Do not require images on every page.

Recommended severity:

- Homepage/core HIGH PRIORITY unresolved: blocking validation error unless explicit waiver/no-media exception is present in the planning artifact.
- Guide/article HIGH PRIORITY unresolved: warning/revise signal, not a universal build blocker.
- RECOMMENDED unresolved: informational warning.
- NO MEDIA NEEDED: pass when represented as an intentional state with rationale.

### Stable Core Analysis

- Why all future projects inherit it: v2.6 Starter should expose a repeatable technical signal for the most damaging silent media debt.
- Production evidence: unresolved high-priority media could reach technically green state.
- Project-edge alternative: project status docs can track this, but no reusable check means repeated silent misses.
- API/schema impact: no Page Inventory change; optional planning-artifact parser/validator only.
- Coupling impact: bounded coupling to page IDs/routes, not to rights or Human approval semantics.
- Regression protection: media readiness cases A-D from the Stage 1 request.

### Regression Plan

Required tests after approval:

- Homepage HIGH PRIORITY resolved and integrated: PASS.
- Homepage HIGH PRIORITY unresolved: blocking validation error unless explicit waiver/no-media exception exists.
- NO MEDIA NEEDED with rationale: PASS and no requirement for images.
- RECOMMENDED unresolved: non-blocking informational warning.
- Unknown page ID/route in media decision table: validation error.
- Existing empty `media.json` with no media decision table: preserve default Starter PASS.

### Classification

SHOULD FIX, with Human approval needed on exact severity wording. It may become MUST FIX if Human wants Stage 2 to enforce homepage high-priority unresolved as blocking.

## YouTube / Third-Party Fallback Decision

### Decision

DEFER FOR THIRD-GAME EVIDENCE and keep as PROJECT-EDGE PATTERN for v2.6 Starter.

### Reasoning

v2.5 already has a narrow reusable YouTube contract:

- media manifest stores canonical 11-character ID;
- `VideoEmbed.astro` renders `youtube-nocookie.com`;
- media audit checks iframe source, title, lazy loading, permissions, fullscreen, privacy policy, and responsive wrapper.

Afterworld showed that a painted iframe can fail visually and a project-edge fallback can work. However, one project-edge recovery does not prove the exact fallback UI belongs in Stable Core. Adding fallback UI now risks expanding component API expectations, styling responsibility, and provider-specific behavior.

### Future Adoption Threshold

Adopt into Stable Core only if another production project repeats the blank third-party player failure and the same small solution still fits without:

- schema inflation;
- generic iframe abstraction;
- provider framework;
- media DSL;
- meaningful API complexity;
- broad new visual policy in Starter.

### Regression If Later Adopted

- `VideoEmbed.astro` renders visible fallback label/play affordance/source link.
- iframe remains privacy-enhanced and accessible.
- fallback does not require new manifest fields.
- blocked iframe state appears intentional in screenshot review.

## SOP / Master Prompt Alignment

The proposed Starter changes satisfy frozen upstream requirements without duplicating them:

- GAME_SOP remains methodology authority.
- Master Prompt remains execution-controller and gate authority.
- Starter remains reusable technical implementation.
- Runtime Page Inventory remains publication SSOT.
- Media lifecycle remains in `MEDIA_DECISION_TABLE.md`, `CURRENT_STATUS.md`, reconciliation, and Human review artifacts.
- Starter does not own Game Recognition decisions.
- Starter does not own rights decisions.
- Starter does not own Human media waiver decisions.
- Starter does not own competitor benchmark decisions.
- Starter does not own Human Visual approval.

## Architecture Principles

High Cohesion:

- Content media rules stay in media validation/catalog/rendering files.
- Site chrome validation stays near config/layout/header checks.
- Planning readiness checks stay in validation scripts, not page renderers.

Low Coupling:

- Chrome assets are validated by path/existence/accessibility role, not forced into `media.json`.
- Media readiness references Page Inventory IDs/routes but does not alter publication data.
- YouTube fallback remains edge until stronger evidence prevents Stable Core from coupling to provider failure UI.

Modular Design:

- `src/data/schemas/media.ts` continues to define content media assets.
- `scripts/media-validation.ts` can expose separate content-media and chrome-asset helpers.
- `scripts/validate-site.ts` remains the CLI aggregation point.
- Header/nav remain presentation components.

Adaptable Design:

- Projects with no logo still use the text mark.
- Projects with semantic logo can use `<img alt="...">`.
- Projects with no useful media remain valid when planning explicitly supports `NO MEDIA NEEDED`.

Stable Core / Flexible Edge:

- Stable Core receives only the role-boundary bug fix and lightweight readiness signal.
- Flexible Edge keeps project-specific fallback visuals, game-specific media richness, rights decisions, and visual identity.

## Over-Engineering Review

Explicitly rejected:

- `AssetRoleEngine`

## Stage 2 Implementation Addendum

Human approval was provided for local Stage 2 implementation with the following final decisions:

- Content media vs site chrome separation was implemented as Stable Core.
- Logo/header validation was implemented with one narrow optional `brand.logoPath` config field.
- Media readiness was implemented as an optional planning-only signal from `MEDIA_DECISION_TABLE.md` when present.
- Homepage `HIGH PRIORITY` unresolved media is blocking technical readiness.
- Non-homepage `HIGH PRIORITY` unresolved media is a non-blocking warning/revise signal.
- `RECOMMENDED` unresolved media is informational only.
- `NO MEDIA NEEDED` remains valid and does not create a media quota.
- YouTube/third-party visual fallback remains deferred as a project-edge pattern.
